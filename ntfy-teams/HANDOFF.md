## 0. 三十秒版

| 問題 | 答案 |
|---|---|
| 這個外掛在哪 | `cordis-plugins/ntfy-teams/`（DSH profile `web` 的外掛 bundle） |
| 改完之後一定要做什麼 | `node build.js`，然後跑 `client-offline.js` |
| 為什麼要 build | `lib/client.js` 是**建置產物**，`lib/core.js` 會被內嵌進去 |

## 1. 開發理念

這一節是這個外掛的「憲法」。**改動時如果和這裡衝突，先確認是不是要修憲，不要默默繞過。**

### 1.1 註解必須是可驗證的事實，不能是聽起來合理的推測

這是本專案最硬的一條規矩，因為違反它的代價最高。

註解裡寫「實測：…」的時候，**那個數字必須真的量過**。寫「這樣比較快」
「理論上不會有問題」這類話沒有價值，還會誤導下一個人。

反例（真實發生過）：我曾把「取消訂閱」按鈕的顏色從 `state-error`
改成 `--dsw-static-red-600`，註解寫「600 階壓得住、實測對比不足」。
後來去查令牌定義才發現：

```
--dsw-static-red-500 : #ef4444
--dsw-static-red-600 : #ec1313      ← 跟 --dsw-alias-state-error-primary 完全相同
```

**兩者是同一個值，「換了階數」根本沒有視覺差別**，那句「實測對比不足」是編出來的。
所以：**寧可寫「還沒量過」，也不要寫一個聽起來很合理的假事實。**

### 1.2 唯一的持久層是宿主的 YAML

`config.yml`（設定）+ `secrets.yml`（帳密，0600）就是全部。
**不再有 localStorage、也不再有第二份真相。**

為什麼這條要寫成憲法：這個外掛最難纏的一整類 bug（見 §3.A）全部來自
「有兩份清單互相覆蓋」。當年同時寫 localStorage 與宿主，兩邊會互相蓋回去，
症狀是「刪掉的主題又出現」「重新整理後設定被舊值蓋掉」。

現在的做法：

* `core.store` 是**純狀態**，不做 I/O；
* 要落地就只有一條路：PUT 給宿主 → 宿主寫 `config.yml`；
* 舊版留在瀏覽器裡的 `ntfy-teams*` key 由 `purgeLegacyStorage()` **只刪不寫**清掉。

> ⚠️ 新增任何持久化之前先問：**能不能不要？** 幾乎每次答案都是能。

### 1.3 清單有兩份，就一定會不同步

`store.topics`（畫面上的即時狀態）和 `readConfig().topics`（記憶體設定）
**必須在任何變更後都一致**。這件事有專門的函式 `syncTopicListToConfig()`，
刪除與新增都要呼叫（見 §3.B）。

**只要有人加了第三條會改訂閱清單的路徑而忘了同步，這個 bug 就會復活。**

### 1.4 不要輪詢

使用者明確要求過：即時推送就是一條 SSE，**沒有定時打 API**。
理由不只是禮貌 —— ntfy 的限流實測約 6 次/短窗口，輪詢會直接把自己鎖死。

連「示範圖表的動態效果」都遵守這條：看板的示範資料**跟著真實事件換種子**
（切主題、開面板），不是用 `setInterval` 定時跳。

### 1.5 只用主題令牌；例外必須登記

深色／淺色主題都要能用，所以顏色一律走 `--dsw-*` 令牌。

**唯一的例外是使用者欽定的固定灰階**：抬頭底線 `#ddd`、看板左緣 `#ddd`、
看板底部保留區上緣 `#eee`、焦點 `#333`。
這些是「規格」不是「主題語意色」，不該跟著主題漂移。

`client-offline.js` 裡有一條測試 `樣式表只用主題令牌，不寫死顏色`
用 **「扣掉已知例外後必須為空」** 的方式把關。要新增例外就必須去改那份白名單
並寫清楚理由 —— 這個摩擦是刻意的。

### 1.6 使用者可見文字一律繁體中文

`test/zh-tw-check.js` 會掃出簡體字。這個外掛的 UI、提示、`aria-label`、
`title` 全部是 zh-TW。

⚠️ **程式碼內部的註解不受此限**（目前註解以簡體為主，這是歷史共業），
但**新增的使用者可見文案一定是繁體**。

## 2. 設計過程（決策脈絡）

### 2.1 為什麼 `lib/client.js` 是建置產物

`dsh-client-modules` **只送一個 client 檔案上瀏覽器** —— 它解析
`package.json` 的 `exports["./client"]`，就這一個路徑，沒有「額外檔案」欄位。

所以隔壁的 `lib/core.js` 永遠不會被執行（實測：`GET /plugins/ntfy-teams/core.js`
→ 404）。而且**檔案順序也不可依賴**，因為 combo script 把每個檔案包成 lazy body。

因此：`build.js` 把 `core.js` 內嵌進 `client.js` 的
`// @@CORE_BEGIN@@ … // @@CORE_END@@` 區塊，讓 `client.js` 自足。
重複執行是幂等的。

```
改 lib/core.js      →  node build.js  →  lib/client.js 才有那段程式碼
改 lib/client.js 的標記區塊之外  →  不用 build（但 build 一次也無害）
```

### 2.2 為什麼宿主半邊不做 ntfy 代理

瀏覽器直接打 ntfy（`fetch` + SSE），宿主只負責兩件事：
**存設定**、**發訊息時代理一次 POST**。理由：

* ntfy 的認證頭／權杖不必經過宿主，少一層可以少一層出錯；
* 宿主不需要維持長連線，重啟不會斷掉使用者的即時推送。

### 2.3 為什麼 SSE 不用 `EventSource`

`EventSource` 不能自訂 `Authorization` 標頭。ntfy 的 private 主題需要
Basic / Bearer 認證，所以自己讀 `fetch` 的 `response.body` 串流並解析 SSE 框架。

### 2.4 為什麼是一條合併的 SSE，不是每主題一條

`GET /<a,b,c>/sse` 一次訂閱所有主題。這樣連線數固定為 1，不會隨主題數增長。

⚠️ **代價（見 §3.C）**：只要**其中一個**主題沒權限，ntfy 回整個 403，
**整條連線**都收不到。這是一個尚未處理的已知限制。

### 2.5 失敗重試：節奏是規格，不是實作細節

`1s → 2s → 4s → 8s → 16s → 30s`（之後維持 30s，永不放棄）。
這是使用者指定的，`client-offline.js` 有測試釘住。
側欄也要顯示 `retrying` 狀態（不是 `error`）—— 「正在重試」和「壞了」是兩件事。

### 2.6 清單「等於」宿主，不是「補上」宿主

`syncSettingsFromHost()` 的同步邏輯：**先加缺的，再移除多的**。

一開始只做了「加」（`ensureTopic`），於是 store 只會單向增長 ——
宿主已經刪掉的主題在 store 裡永遠不會消失。這是「刪掉又出現」的早期成因之一。

> 教訓：**同步一定要有「減」的那一半。**

### 2.7 看板：示範資料要誠實

看板的圖表是**示範（demo）**，資料是本地用種子產生的隨機漫步，不是真實統計。
所以每張卡片右上角都有一個琥珀色 `示範` 標籤，測試也釘住「四張卡片 = 四個標籤」。

**隨機資料不能冒充真實統計。**

技術上刻意用 `mulberry32` 種子式 PRNG 而不是 `Math.random()`：

* `Math.random()` 會讓 **React 每次重繪都拿到新數字** → 圖表自己抖動，那是閃爍不是動態；
* 種子式保證「同一輪 → 同一組數字」，要換一輪就換種子。

## 3. 踩過的坑（按危險程度排序）

> 每一條都是**真的發生過**的。寫下「症狀 → 根因 → 教訓」，
> 因為下一次它會換個形式再來。

### A. 「刪掉的主題又回來了」（前後查了很多輪，跨了 4 個不同根因）

**症狀**：取消訂閱某個主題，當下成功；重新整理或切換畫面之後它又出現。

這是本外掛最貴的一個 bug，因為它**有四個獨立的成因**，而且每次修掉一個
都以為結束了。依時間順序：

1. **v1 遷移重匯入** —— 舊版從 localStorage 讀回清單再寫進宿主。
2. **種子判別錯誤** —— 分不清「宿主從來沒有設定檔（該播種預設主題）」與
   「使用者把主題刪光了（不該塞回去）」。後來用 `configMissing` 區分。
3. **同步只加不減** —— 見 §2.6。
4. **刪除只清了 store，沒清記憶體設定** —— **這是真正的元凶**，見下面 B 條。

**教訓**：
* 同一個症狀可能有多個成因，**修掉一個不等於修好**；
* 回報「又回來了」的時候，要問清楚**具體的重現步驟**（見 B 條，使用者給的
  兩步重現是整個調查的轉折點）。

### B. ★ 兩份清單不同步（最容易復發的一條）

**症狀**（使用者提供的決定性重現步驟）：

```
1. 刪除主題 → 切到別的畫面 → 切回來     → 主題回來了 ❌
2. 刪除主題 → F5 → 切回來                → 主題沒有回來 ✅
```

**根因**：訂閱清單有**兩份**，用途不同：

| | 用途 |
|---|---|
| `core.store.topics` | 畫面上的即時狀態（權威） |
| `core.readConfig().topics` | `bootStore()` 在面板重掛時用來**起一份 store 的種子** |

開機時 `syncSettingsFromHost()` 會把宿主的 topics 寫進**記憶體設定**，兩份一致。
但**刪除只動了 store**，記憶體設定裡還留著那一個 ——
面板重掛時 `bootStore()` 就把它從記憶體設定灌回 store。

**為什麼 F5 就不會**：重新載入會重跑模組，記憶體設定變空，只從宿主 YAML
（已經沒有它了）重建。

**為什麼測試一直抓不到**（重要）：探針主題通常只進了 store、**沒進記憶體設定**
（因為探針直接呼叫 `store.ensureTopic`），所以少了「記憶體設定裡有殘留」這個前提，
重掛時自然不會復活 —— **看起來像已經修好了**。
要重現必須先讓記憶體設定也有那個主題。

**修法**：`syncTopicListToConfig()` —— 讓記憶體設定與 store 在任何變更後對齊。
掛在**刪除**與**新增**兩條路徑上（新增是同一類 bug 的反方向：
新增完切走再切回來，主題會消失）。

**教訓**：
* **同一個資料有兩份表示法，就一定會不同步。** 能合併就合併，不能合併就要有
  一個「對齊」的地方，並且每一條寫入路徑都要呼叫它；
* 寫測試要**照著使用者的重現步驟走同一條程式路徑**。繞過 UI 的探針會掩蓋 bug。

### C. 一個私有主題的 403 打死整條即時連線（**尚未處理**）

**症狀**：合併 SSE 只要有一個主題沒權限，ntfy 回整個 403，
**所有主題都沒有即時推送**。

連帶影響：認證提示反覆出現、「需要認證」旗標被反覆設 true，
讓人誤以為是認證壞了。

**建議修法**：把需要認證的主題拆到**第二條連線**（公開 `pub_*` 一條、
私有主題一條），讓公開主題的推送不被 403 拖垮。
代價是多一條常駐連線（仍在限流額度內）。

**現況**：已向使用者說明，尚未實作。

### D. ★ 探針會污染使用者的真實設定

**症狀**：使用者的設定莫名被改回去／刪掉的主題被還原。

**根因**（兩層，第一層是主因）：

1. **宿主啟動時沒有設 `NTFY_TEAMS_SETTINGS_DIR`。**
   這個變數**程式碼是支援的**（`lib/index.js` 的 `settingsDir()` 讀它，
   再傳給 `createStore({ dir })`），所以「設定搬到別處」本身是可行的；
   但**執行中的那個宿主不是帶著它啟動的**，因此它用預設目錄 ——
   也就是使用者的真實 `config.yml`。
   瀏覽器探針跑的是宿主上的 `apply()`，它**無從得知**這件事，
   於是必然寫到使用者的真檔。

2. **`config-store.createStore()` 沒給 `dir` 時會退回 `process.cwd()`。**

   ```js
   const dir = options && options.dir ? String(options.dir) : process.cwd();
   ```

   這是個腳槍：任何直接 `createStore()` 的程式（例如我寫過的探針）
   **會依「從哪個目錄執行」決定要讀寫誰的設定**。
   實測：從外掛目錄執行 `createStore()`，它讀到的就是使用者的真檔。

   要驗證環境變數有沒有生效，**一定要走宿主那條路**：

   ```js
   // ✅ 宿主怎麼做，你就怎麼做
   createStore({ dir: process.env.NTFY_TEAMS_SETTINGS_DIR || <預設目錄> })
   // ❌ 這個會讀 cwd，可能正好是使用者的外掛目錄
   createStore()
   ```

**後果**：探針常見的寫法是「整份備份 → 測試 → 整份還原」，
**使用者在那段期間做的任何編輯，都會被還原動作蓋掉。**

這件事造成兩個嚴重後果：

1. 使用者的編輯被覆蓋（真實的資料損失）；
2. **製造了假 bug 證據** —— 我因而長期在查「刪除為什麼沒寫出去」，
   但實際上刪除每個環節都正常，只是被我的還原蓋掉了。

**教訓**：
* **驗證工具本身必須被驗證。** 探針是會寫入的程式，它也是嫌疑犯；
* 對使用者的真實資料，**預設只讀**。要寫入就必須先講清楚、並且用外科手術式的
  清理（只移除自己加的東西），不要整份還原；
* 測試資料要用**自己產生的拋棄式識別名**（例如 `pub_probe<隨機>`），
  這樣才分得清「誰留下的」；
* **想徹底隔離，就讓宿主帶著 `NTFY_TEAMS_SETTINGS_DIR` 啟動**（見 §8 TODO #5）。

### E. 驗證工具本身出錯（不是產品的錯）

這一類最耗時間，因為它讓**修好的東西看起來壞掉**，或**壞掉的看起來修好**。

實際發生過的例子：

| 症狀 | 真相 |
|---|---|
| 開機後主題「復活」 | 其實是**我的探針在整份還原** |
| 證明「測試守不住 bug」 | 其實**我的移除腳本沒真的改到檔案**（移除失敗卻沒發現） |
| 截圖裡看不到 footer | 其實 footer 正確渲染，是**我的取景框到另一個面板** |
| 探針說「沒有未讀線」 | 其實探針**繞過了 UI 的前置步驟**（見 §3.F） |
| 探針找不到甜甜圈分段 | 其實是**我的 class 比對寫錯**（見 §4.7） |

**教訓**：改結論之前，先確認「**我怎麼知道我知道**」。
量測腳本輸出「預期之外的結果」時，**先懷疑量測**。

### F. `setActiveTopic` 會把未讀歸零（設計如此，但探針常忽略）

**症狀**：未讀線畫不出來，切過去之後未讀永遠是 0。

**根因**：`setActiveTopic()` 會把該主題未讀歸零（「正在看」=「已讀」）。
所以**未讀數必須在 `setActiveTopic` 之前交出去** —— 這是 `TopicBar.select()`
裡的 `onWillActivate` 在做的事。

**探針的錯**：直接呼叫 `store.setActiveTopic()` 會**跳過**那一步，
於是未讀永遠是 0、線畫不出來 —— 看起來像產品的 bug，其實是探針走錯路徑。

**教訓**：同 B 條 —— **測試要走使用者的真實路徑**。

### G. 建置產物與瀏覽器快取的時序

* `lib/client.js` 是建置產物：**改 `core.js` 不 build，瀏覽器就看不到**；
* bundle 網址帶的 `rev=` 是 DSH 用 **`mtimeMs` + `ctimeMs` + `size`** 算出的 sha1
  （12 hex，見 `dsh-client-modules` 的 `artifactRevision`）。所以每次 build 都會變。
* ⚠️ **F5 可能仍拿到舊的 JS。改完請按 `Ctrl+Shift+R`（硬重載），
  並告訴使用者也要這樣做。**

曾經有一次「硬重載後還是壞的」，我據此推論「不是快取問題」——
方向對了，但**當下我沒有先確認使用者載入的是哪一版**，白白多繞一圈。
現在可以這樣查：

```js
// 在 Console 裡看目前載入的 bundle 版本
performance.getEntriesByType('resource')
  .map(e => e.name).find(u => u.includes('ntfy-teams'))
```

### H. 只有一個 client 檔案（再強調一次，因為它決定整個架構）

見 §2.1。如果哪天想拆檔，先確認 `dsh-client-modules` 是否已經支援多檔；
在它支援之前，**拆檔 = 那個檔不會被執行**。

### I. ★ 兩個「留白／容差」方向相反，功能就永遠差一步

**症狀**：訊息串右側的日期跳轉列（見 README「日期跳轉列」）裡
「下一天」能動、「最後一則」能動，但**「上一天」只往上挪一點點**，
永遠回不到真正的上一天。

**根因**：兩個常數方向相反。

```js
jumpTo(wrap)          → box.scrollTop = wrap.offsetTop - 8   // 往上留 8px 白
currentDayIndex(box)  → wraps[i].offsetTop <= box.scrollTop + 8   // 往下容差 8px
```

「跳到某一天」會停在 `offsetTop - 8`；而判斷「目前在哪一天」時用 `+8`，
於是**剛跳過去的那一天被算成「還沒到」**，系統認為還在前一天 →
按「上一天」只是把捲動位置拉回當天開頭（實測：151 → 119，而不是回到第一天）。

**修法**：容差改成 **18px**（> 8px 留白 + 次像素誤差），且**方向一致** ——
讓「剛跳到某天」時它的 `offsetTop` 仍大於 `scrollTop`，
那一天就被認成「目前這一天」。

**教訓**：
* 只要有一組常數是「留白」而另一組是「容差」，**就要驗證它們的方向關係**，
  不能各自看起來合理就放過；
* 這種 bug 的特徵是「**差一步**」而不是「完全沒反應」——
  按鈕會動、只是動得不對，比完全不動更難察覺。

### J. class 前綴誤中（第三次了，所以寫進這裡）

`ntfy-teams-day` 這個前綴在新增 `.ntfy-teams-daynavbtn`（日期跳轉列按鈕）之後，
**同時命中了兩種節點**，於是「應分成 3 天」變成 6。

同一個家族已經踩過三次，方向兩種：

| 前綴 | 誤中的 | 後果 |
|---|---|---|
| `ntfy-teams-header` | `ntfy-teams-headeracts` | **多算** |
| `ntfy-teams-msg` | `ntfy-teams-msgbody` 等子元素 | **多算**（5 則算成 15 個） |
| `ntfy-teams-day` | `ntfy-teams-daynavbtn` | **多算**（3 天算成 6 個） |

**對策**：`client-offline.js` 裡已經有一個共用的 `hasDayToken()`；
新寫的比對請**切成 token 再比**，不要用 `indexOf`：

```js
const has = (n, token) => (n.cls || '').split(/\s+/).indexOf(token) !== -1;
```

### K. 測試替身沒有 DOM：`ref.current` 是 null

訊息串的捲動邏輯（跳到某一天、捲到底）需要 `boxRef.current.querySelectorAll`、
`offsetTop`、`scrollTop`… 這些在 `client-offline.js` 的測試替身裡**都不存在**，
所以**離線測試驗不到捲動行為**。

**對策**：
* 離線測試只驗**結構**（三顆按鈕、標籤、可不可按、節點順序）；
* 捲動**位置**交給真實瀏覽器（`browser-verify.js`）驗，並在測試註解裡寫清楚
  為什麼不在這裡驗，避免下一個人以為「漏了」而補一個假 DOM 進去。

### L. ★ 有**兩個**地方會把未讀歸零，少改一個就等於沒改

**症狀**：store 的未讀明明 +1 了（有 log 為證），但面板上「N 則新訊息」提示條
永遠不出現，`unreadByTopic` 讀回來又是 0。

**根因**：清未讀的入口有兩個，而且**在不同的層**：

| # | 位置 | 條件 |
|---|---|---|
| 1 | `core.addMessages` 的 `seesLatest` | 看得到 **且貼底** 才算已讀（新規則） |
| 2 | `MainPanel` 的 `readRef` effect | 原本是「面板每次多了新訊息就 `markRead(active)`」——**無條件** |

只改 (1) 的話，(2) 會在下一輪把剛累加的未讀清掉。實測抓到的方式是
**攔截 `markRead` / `markReadToLatest` / `setActiveTopic` / `removeTopic`，
比對呼叫前後的未讀值** —— 一眼看出是 `markRead` 把 1 變 0。

**連帶的第二個坑**：`markReadToLatest` 原本**只推進「讀到哪」、不清未讀**
（`markRead` 才是清未讀的那個）。於是「點提示條跳過去」之後未讀留著、
提示條不會消失 —— 因為 (2) 那個 effect 只在**訊息數變化**時才跑，
而「跳過去」只是捲動、訊息數沒變。

修法：`markReadToLatest` 也清未讀（「讀到最新」語意上就等於沒有未讀）。

**教訓**：
* 「同一個狀態有兩個地方會寫」跟「同一份資料有兩份表示法」一樣危險 ——
  **改規則之前先把所有寫入點找出來**（grep 那個函式名，不要只改你看到的那個）；
* 遇到「明明設了卻沒生效」，最快的方式是**攔截所有可能的寫入點、
  記錄呼叫前後的值**，而不是繼續讀程式碼猜。

### M. 別人的訊息「送達了但沒算未讀」——先確認判定值，不要猜

這一輪的排錯靠的是**把判定印出來**，而不是讀程式碼推理。插入一行 log
（`isViewing` / `isFollowing` / `seesLatest` / `mine` / `newCount` / `source`）
之後一次就定位：

```
{ newCount: 1, source: "sse", isViewing: true, isFollowing: false,
  seesLatest: false, mine: false }     ← 判定完全正確，問題在別處
```

**兩個教訓**：
* **先確認「判定對不對」，再懷疑「判定之後的事」。** 這裡判定是對的，
  所以 bug 一定在「誰把結果改掉了」；
* ⚠️ **插 log 要插對檔案**：`lib/client.js` 的 `@@CORE_BEGIN/END` 之間是
  **建置產物**，改那裡會被 `node build.js` 覆蓋掉。`addMessages` 的真正來源是
  `lib/core.js`（實測：插在 client.js 的版本永遠沒被執行到，白白多繞一圈）。

### N. ★ 宿主把設定**記在記憶體**，直接改 `config.yml` 沒有用

**症狀**：明明已經把測試主題從 `config.yml` 刪掉了，GUI 裡它還在。

**根因**：執行中的宿主把 `config.yml` 讀進記憶體之後就**以記憶體為準**。
直接編輯檔案它不會知道；而且**下一次任何寫入**（拖看板寬度、改設定、加主題）
都會用它記憶體裡的舊清單把檔案**蓋回去** —— 刪掉的主題就復活了。

這正是「刪除的主題又回來了」在開發階段的另一個成因，也是為什麼**探針留下的
測試主題總是清不乾淨**（我改了檔案，但宿主記憶體裡還留著，下次寫入又寫回來）。

**正確做法**：要改設定就走宿主認可的寫入路徑：

```js
// ✅ 先 GET 拿完整的 config，只改要改的欄位，再 PUT 回去
const cur = await fetch('http://127.0.0.1:3080/ntfy-teams/settings').then((r) => r.json());
await fetch('http://127.0.0.1:3080/ntfy-teams/settings', {
  method: 'PUT',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ config: { ...cur.config, topics: ['pub_dsh'] } })
});
```

⚠️ **只用 delta 會把其他欄位清掉**：`writeConfig` 是整份覆寫，
所以一定要先 GET 拿完整的再改（實測：只 PUT `{topics}` 會讓
identity / aliases / dashboardWidth 全部消失）。

**教訓**：
* **「檔案改了」不等於「系統改了」** —— 有記憶體快取的地方，改檔案是無效的；
* 清理測試資料時要**從系統的入口**清（PUT），不能從底層檔案清。

### O. 設定欄位漏掉一端，功能就「看起來能開但其實沒作用」

加一個新的持久化設定（例如自動回應的開關）時，**有三個地方要一起改**：

| # | 位置 | 漏了會怎樣 |
|---|---|---|
| 1 | `core` 的 `CONFIG` 預設 + `readConfig` 正規化 + `saveConfig` 合併 | 設定存不進記憶體 |
| 2 | `buildSettingsPayload`（寫給宿主的 payload） | **勾了不會進 `config.yml`**，重新整理就沒了 |
| 3 | `syncSettingsFromHost`（從宿主讀回來） | 重開之後讀不到，設定形同虛設 |

實測踩過：只做了 (1)，勾選後 `config.yml` 裡根本沒有 `autoApprove` 這個欄位 ——
**功能看起來正常（UI 有反應），實際上完全沒作用**。

**自查方式**：加完欄位後，勾一次設定，然後 `cat config.yml` 看那個欄位在不在。

### P. 「兩個 checkbox」的第二個：改行為之前先想清楚它**覆蓋**了什麼

加「永遠滾到最新」時，真正的風險不是 UI，而是它**跟既有的捲動規則打架**。

既有的規則是「自己發的才自動跟隨、別人發的浮提示條」（§4 未讀那一段）。新開關的
語意是「不管誰發的都跟隨」—— 也就是它**必須覆蓋**那條規則。實作時要注意兩點：

1. **條件要寫成「開關打開 **或** 貼底」**，不能只寫「貼底」：
   ```js
   if (!props.stayAtBottom && !stickRef.current) return;   // ✅
   if (!stickRef.current) return;                          // ❌ 開關形同虛設
   ```
   `stickRef` 在使用者自己往上捲之後會變 false，但這個開關的語意就是「不管怎樣
   都回到最新」—— 兩者要分開判斷。

2. **要記得回頭把 `stickRef` / `streamFollowingRef` 設回 true**，否則下一次
   別人發訊息時又會被判成「沒貼底」，開關就只生效一次。

**教訓**：新功能如果會**改變既有行為**，先列出「它跟哪幾條規則重疊、誰覆蓋誰」。
這裡的覆蓋關係是**刻意的**（使用者要的就是打破保護），所以要在 UI 文案上寫清楚
（「不管誰發的」），否則使用者會以為它跟提示條是同一件事。

### Q. 「勾了沒反應」：切換當下要主動捲一次

「永遠滾到最新」勾選的那一瞬間，**不會有任何新訊息**，所以光靠「新訊息進來才捲」
的 effect 是完全沒反應的 —— 使用者會覺得功能壞了。

做法：勾選時立刻呼叫一次捲到底。因為捲動容器在 `MessageList`、開關在 `MainPanel`，
用一個模組層的 ref（`streamJumpToEndRef`）由前者註冊、後者呼叫。

⚠️ **ref 要在卸載時清掉**（`return () => { ref.current = null; }`），
否則面板重掛之後會呼叫到已卸載元件的舊閉包。

### R. 「這個控制項到底有沒有用途」——先查資料有沒有被呈現，再決定拿不拿掉

使用者回報：「『預設』下拉框是幹什麼的，沒有用途取消它」。

查證的結果是**一半對**：
* 那個下拉框是**優先級**（ntfy 的 `priority` 1..4）；
* 它確實有送出（`publishMessage` 會帶），但當時**UI 完全不呈現優先級** ——
  使用者選了「高」，畫面上沒有任何差別，所以看起來像沒用途。

⚠️ **我當下的判斷是錯的**：我把「UI 沒呈現它」推論成「它沒有用途」，直接拿掉了，
還寫了一段「留著會誤導」的註解。使用者立刻回來澄清「預設是優先級，還是要的」。

**兩個教訓**：
* **「UI 沒呈現」≠「沒有用途」**。`priority` 影響的是 ntfy **自己**的推播
  （手機通知大小聲、是否打穿勿擾），那是在這個面板之外發生的事。
  判斷一個控制項該不該存在，要先問「它的效果在哪裡發生」，
  而不是「我在這個畫面裡看到它了嗎」；
* **使用者說「取消它」時，先確認他要的是取消「這個東西」還是「這種呈現方式」。**
  這次要留的是功能、要換的是 UI。不確定的話，改之前先問一句比改錯再改回來便宜。

**最後的做法**：保留功能，把 `<select>` 換成**分段控制**
（四段一次看到全部 + 1～4 格強度指示 + 選中白底）。
下拉框的問題從來不是「它沒用」，而是「看不出它有什麼用」。

### S. 標籤文案：短標題 + tooltip，不是一整句塞在標籤裡

回饋：「checkbox 的文本，解釋太多了，簡短一些」。

原本兩個 checkbox 的標籤是完整句子（把觸發字串、回什麼、只認即時推送全寫進去），
理由是「這是會代替使用者發言的功能，不能讓他自己猜」。**理由沒錯，位置錯了** ——
那些細節每一眼都要重讀，變成閱讀成本。

**做法**：標籤只留名字，細節搬進 `title`（tooltip）。

| | 之前 | 現在 |
|---|---|---|
| 自動批準 | `自動回應：出現 /approve session 時回覆 /approve` | `自動批準 /approve` |
| 永遠滾到最新 | `永遠滾到最新：不管誰發的訊息都自動捲到最底` | `永遠滾到最新` |

**原則**：標籤回答「這是什麼開關」，tooltip 回答「它的規則細節」。
判斷標準是「使用者每次看到它需不需要知道這件事」。

⚠️ 但**不能把必要的限制只留在 tooltip 而標籤完全不提** —— 例如自動批準多了一個
`hermes-agent` 標籤條件，如果 tooltip 沒寫，使用者會以為「有人打出那句話就會回」，
然後納悶為什麼沒反應。**測試有釘住這一句**（`client-offline.js`）。

### T. 「准」是簡體字，繁體是「準」—— 而我一度把檢查器改成錯的

`zh-tw-check` 抓到我在標籤裡寫的「自動批准」含簡體字 `准`（U+51C6）。
我當下的反應是「准在繁體裡也用啊，是檢查器誤報」，於是**去改了檢查器**。

**錯的是我。** 查《教育部重編國語辭典》：繁體是「**批準**」（`準` U+6E96），
`准` U+51C6 是簡體。檢查器從頭到尾都是對的。

**教訓**：
* 被工具指出錯誤時，**先假設工具是對的**，去查證再決定要不要改工具。
  這次我反過來，差點把一個正確的檢查改壞（而且已經動手了）；
* 我確認「準是繁體」的方式是**查辭典**，不是憑語感 —— 這種字最容易憑印象出錯；
* 順帶發現檢查器**真的有兩個誤列**（跟這次的「准」無關）：
  * `客`（U+5BA2）是簡繁同形（「客戶端」在繁體就是這樣寫），卻被列進
    `SIMPLIFIED_ONLY` → 任何出現「客戶端」的地方都誤報；
  * `SIMPLIFIED_WORDS` 是為**介面字串**設計的，拿來掃技術文件會爆大量誤報
    （實測 14 筆裡只有 1 筆真的：「確保存在」被「保存」誤中、「令牌」「文件」
    被判成簡體詞）。
  兩者都已處理：`客` 移到 `SHARED_CHARS`；文件掃描改成**只掃簡體專屬字、
  而且只警告不改 exit code**（一個一直響的檢查會訓練人忽略它）。

## 4. 動這份程式之前要知道的細節

### 4.1 路由只認精確路徑

客戶端沒有 `ctx.remote`，只能用**精確的 HTTP 路由**跟宿主溝通：

* `GET/PUT/POST /ntfy-teams/settings`
* `GET/PUT/POST /ntfy-teams/session`

**POST 是必要的**（不是為了 REST 美感）：`navigator.sendBeacon` 只能發 POST，
而頁面卸載時要靠它把還沒送出的設定補送出去（見 §4.3）。

### 4.2 寫回宿主是 400ms debounce（但刪除是立刻）

連續輸入（拖看板寬度）走 400ms debounce 才對。
但**刪除是破壞性的一次性動作**，必須 `writeSettingsNow()` 立刻送 ——
否則「刪完馬上重新整理」時 debounce 會被卸載吃掉，刪除就遺失了。

頁面卸載時另有 `sendBeacon` 補送。

### 4.3 測試替身的限制

`test/client-offline.js` 用一個極簡的 React 替身。幾個必須知道的限制：

* **hook 槽位會沿用**：同一個 harness 先畫 A 再畫 B，可能會拿到前一棵樹。
  需要不同狀態就 **`freshPanel()` 開一個新的**。
  （但也有例外：`TopicBar` 需要保留自己的 state 時要在**同一個** harness 裡重畫。）
* **`walk()` 是前序走訪**：`nodes[i-1]` 不一定是 DOM 的前一個兄弟。
  找「某節點之前最近的 X」要往前掃，不要直接取 `i-1`。
* **`walk()` 不會捕捉 render 期間的例外**：某個子元件丟錯的話，
  樹會被**靜靜截斷**（沒有任何錯誤訊息），症狀是一堆不相關的測試同時失敗。
  看到大量測試一起壞掉，先懷疑「有東西在 render 時丟錯」。

### 4.4 主題令牌：這個主題裡 `brand-primary` **不是彩色**

實測（在 `.ntfy-teams-header` 上讀 computed style）：

```
--dsw-alias-brand-primary        = #0f1115   ← 跟 label-primary 完全相同！
--dsw-alias-label-primary        = #0f1115
--dsw-alias-state-success-primary= #22c55e
--dsw-alias-state-error-primary  = #ec1313
--dsw-alias-state-warn-primary   = #f59e0b
--dsw-alias-bg-layer-1 / layer-2 / base = #fff（三個都是純白！）
```

**所以「用品牌色畫一個彩色的東西」在這個主題下不會成功，永遠是黑的。**

要真正的彩色，用**設計平台層的固定色票**（定義在 `body` 上、不隨主題變）：

```
--dsw-static-blue-500     #3b82f6
--dsw-static-amber-500    #f59e0b
--dsw-static-green-500    #22c55e
--dsw-static-neutral-400  #a2a4a6
--dsw-static-deepseek-500 #4176e6
--dsw-static-red-500      #ef4444
```

⚠️ **色系家族只有 6 個**：`amber, blue, deepseek, green, neutral, red`。
**沒有 violet / purple / pink / teal / cyan** —— 要 4 種以上色相時會不夠用
（看板的甜甜圈第 4 段因此用了 `neutral-400`，它在圖表裡讀作「其他」，
而且不像紅／琥珀帶有錯誤／警告的語意）。

⚠️ 另一個坑：**`--dsw-alias-bg-layer-1` / `-2` / `-base` 都是純白**，
所以「用 layer-2 當 hover」等於沒變化、淡色疊加也看不出來。
本檔的隔行底色改用「**墨色混 3%**」就是為了這個。

### 4.5 CSS specificity：同分時**後出現的贏**

改樣式很容易被這一條咬到，實際發生過兩次：

* `.ntfy-teams-msg--self{flex-direction:row-reverse}` 和
  `.ntfy-teams-msg--active` 同分 → 後者贏 → 編輯中的 chip 變成黑底白字看不清。
  修法：寫更明確的 `.ntfy-teams-topic--editing`（並含 `:hover`）。
* 齒輪的 `.ntfy-teams-iconbtn--gear{color:...}` 同分但**排在基類前面**
  → 基類的 `color` 贏。修法：把覆蓋寫在基類之後。

**教訓**：加覆蓋規則時，不只要看選擇器夠不夠specific，**還要看它在檔案裡的順序**。
（`client.js` 的樣式是一長串 `.concat(...)` 陣列，順序＝陣列順序。）

### 4.6 「反色（inverse）」是使用者要的視覺語意

聚焦中的主題 chip 用**反色**（文字色當底、底色當字）。
⚠️ 但**編輯中**的狀態必須蓋掉反色，否則輸入框會是黑底，文字看不清。
`--editing` 的規則要排在 `--active` 之後。

### 4.7 class 比對要**以 token 為單位**，不能用 `indexOf`

`className` 是**空格串接**的多個 class。踩過**三次**、方向兩種：

* `indexOf('ntfy-teams-header')` 會**誤中** `ntfy-teams-headeracts`（多算）；
* `indexOf('ntfy-teams-msg')` 會**誤中** `ntfy-teams-msgbody` 等子元素（多算）；
* `indexOf('ntfy-teams-day')` 會**誤中** `ntfy-teams-daynavbtn`（多算）；
* `indexOf('ntfy-teams-dseg--') === 0` 會**漏掉**
  `"ntfy-teams-dseg ntfy-teams-dseg--0"`（前綴不在字串開頭，少算）。

**正確寫法**：切成 token 再比。詳見 §3.J。

```js
const has = (n, token) => (n.cls || '').split(/\s+/).indexOf(token) !== -1;
```

### 4.8 SVG 圖稿的注意事項

* **漸層／濾鏡的 `id` 要唯一**：同一個頁面可能有多個面板實例，
  重複 `id` 會讓其中一個圖抓錯漸層。
* **圓環文字的垂直定位不要猜基線**：用 `dominant-baseline:central`
  把每一行各自垂直居中在指定 `y`，不要靠調 `font-size` 猜。
  （連兩個字都在圓心重疊過兩次才修好。）
* 固定 `viewBox` + CSS `width:100%`：這樣不用量 DOM、面板寬度變化也不會變形。

### 4.9 看板的版面約束（都是使用者指定的）

* 看板**不從面板頂端開始** —— 上緣從**抬頭下緣**開始，
  否則會蓋掉抬頭右側的連線狀態；
* 最小寬度 300px（`core.CONFIG.dashboardMinWidth`，**單一來源**，
  UI 不要另寫數字，`aria-valuemin` 與 tooltip 都從那裡拿）；
* 底部有 **130px 保留區**，上緣 `1px solid #eee`；* 底部保留區存在之後，`dashbody` 的 `padding-bottom` 要歸零，
  否則會變成「130px + 18px」兩段留白疊在一起。

### 4.10 四個「使用者欽定的視覺規格」（不要擅自改回令牌）

| 位置 | 值 | 理由 |
|---|---|---|
| 抬頭底線 | `1px solid #ddd` | 使用者指定，不是主題色 |
| 看板左緣 | `1px dotted #ddd` | 同上 |
| 看板底部保留區上緣 | `1px solid #eee` | 同上 |
| 焦點邊框 | `#333` | 同上 |

這四個已經登記在 `client-offline.js` 的 `KNOWN_HEX` 白名單裡。
**新增寫死顏色會被那條測試擋下來** —— 這是刻意的摩擦。

## 5. 反覆出現的使用者需求（改動時不要倒退）

這些是使用者明確要求過的，回歸測試大多有守，但改版面時很容易不小心弄回去：

* **不要用 localStorage** 存任何 ntfy 相關的東西；
* **不要輪詢**；即時推送只能是一條 SSE；
* 重試節奏就是 `1s,2s,4s,8s,16s,30s`，側欄要顯示「重試中」；
* **刪除必須撐過重新整理**（也撐過切換畫面 —— 見 §3.B）；
* 顯示名稱未設定時**不能發送**；
* **不要**伺服器編輯 UI，也不要顯示伺服器位址（連主機名都不顯示）；
* 只有**一個**抬頭容器，底線 `1px solid #ddd`，**所有摘要提示都放在那個容器內**；
* 「編輯」入口是**帶顏色的齒輪**（不是鉛筆、也不可以是「圓 + 放射線」那種像太陽的畫法）；
* **沒有**「收合」按鈕（齒輪就是切換）；
* **沒有**「全部主題共用」這類字眼；
* `pub_dsh` 是**不可改名、不可取消訂閱**的預設主題，且永遠排第一位；
* **只有 `pub_*` 主題免認證**；
* 取消訂閱要有確認，而且確認條是**淡紅色卡片**（警示三角 + 保留／取消訂閱）；
* 編輯中的主題**文字必須看得清**（不要被反色蓋掉）；
* 儲存成功後**自動收合**；
* **儲存成功後要把上一次的錯誤訊息清掉**（改認證 → 連線重置 → 舊錯誤不能留）；
* 切換主題要**捲到「已讀的最新一則」**；
* 自己的訊息**靠右**，而且**頭像也要在右邊**；
* 看板最小 300px；看板底部 130px 保留區 + `1px solid #eee`；
* 訊息串**右側中央**要有跳轉列：**START（第一則）**／向上（上一天第一則）／向下（下一天第一則）／END（最後一則）；
* 焦點中的主題：**自己發的**自動捲過去；**別人發的**不要搶走畫面，改浮出「N 則新訊息」提示條讓使用者自己點；
* 輸入框上方要有**自動批準**的 checkbox：這個主題出現 `/approve session` **且訊息帶 `hermes-agent` 標籤**時自動回 `/approve`（預設關閉、每個主題獨立）；
* 輸入框上方要有**永遠滾到最新**的 checkbox：勾選後這個主題不管誰發的訊息都自動捲到最底（預設關閉、每個主題獨立，會覆蓋「只有自己發的才跟隨」）；
* 看板的圖表是**示範**，必須標示「示範」。

## 6. 開發流程（照這個順序做）

```
1. 先重現            ← 不要跳過。憑猜測改是本專案最大的時間浪費來源
2. 讀附近的註解      ← 很多坑已經寫在註解裡，通常就在你要改的那幾行旁邊
3. 改 lib/core.js 或 lib/client.js
4. node build.js            （改了 core.js 就一定要做）
5. node test/client-offline.js      （最快、涵蓋 UI 邏輯）
6. 跑完整套（見下）
7. 在**真實瀏覽器**驗證一次（Ctrl+Shift+R），並截圖
8. 確認沒有污染使用者的 config.yml
```

### 6.1 完整測試套

```bash
cd cordis-plugins/ntfy-teams

node build.js

node test/core-node.js          # 146 項 · 協定／解析／認證／store（無網路）
node test/config-store-node.js  #  19 項 · YAML 讀寫、權限、原子寫入
node test/host-node.js          #  27 項 · 宿主路由（無網路）
node test/client-offline.js     #  57 項 · UI 邏輯（React 替身）
node test/zh-tw-check.js        #       使用者可見文案不得有簡體

                                 # ↑ 需要真實網路（會消耗 ntfy 額度，非必要不要跑）：
node test/core-live.js
node test/browser-verify.js full2
```

`npm run test:offline` 會跑前五個（上面那五個 `node test/...` 指令）。

> ⚠️ `npm test` 會**連 `core-live.js` 一起跑**（真的打 ntfy、消耗額度）。
> 日常改動用 `npm run test:offline` 就好。

### 6.2 真實瀏覽器驗證

```bash
node test/browser-verify.js eval --expr <一個 .js 檔的路徑>
```

它會開一個 CDP session 連到 `http://127.0.0.1:3080/`，導頁、等 `window.__ntfyTeamsCore`
出現，然後 eval 你給的運算式。

**⚠️ 幾條紀律：**

* 不要加 `--virtual-time-budget`（會讓動畫／佈局時序失真）；
* 結束後把主題還原成「跟隨系統」；
* **不要「整份備份 config.yml → 測試 → 整份還原」**（見 §3.D）。
  要清理就只移除自己加的東西：

```js
// 外科手術式清理：只拿掉自己的探針主題，其他一律不動
const t = fs.readFileSync('config.yml', 'utf8');
fs.writeFileSync('config.yml',
  t.split(/\r?\n/).filter((l) => l.trim() !== '- pub_probe12345').join('\n'));
```

* 探針主題一律用**拋棄式識別名**（`pub_probe<隨機數>`），不要借用使用者的主題。

### 6.3 UI 改動後一定要能證明給自己看

**先量數字，再看截圖。** 這一次的教訓是：截圖取景可能框到別的面板，
但 `getBoundingClientRect()` 不會騙人。

好的驗證長什麼樣（看板底部保留區）：

```js
{
  minHeight: "130px",
  高度: 130,
  borderTop: "1px solid rgb(238, 238, 238)",   // = #eee
  其他邊: "0px/0px/0px",                        // 只有上緣有線
  貼到底: true
}
```

**「看截圖覺得好像對」不算驗證。**

## 9. 最後一句

這個外掛的程式碼本身不複雜 —— **複雜的是它累積起來的那些「為什麼」**。

真正花時間的不是寫功能，而是：

* 分清「使用者回報的症狀」與「真正的根因」（同一個症狀有過四個成因）；
* 認出「是我的量測壞了」而不是「產品壞了」（發生過五次以上）；
* 忍住不要在使用者的真實資料上做實驗。

所以：**改之前先重現，改之後要能證明。**
如果證明不了，就誠實說「還沒驗證過」 —— 那句假事實的代價，
比「不知道」高得多。
