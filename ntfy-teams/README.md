# 團隊協同 · ntfy-teams

在 DSH Web GUI 裡訂閱 [ntfy](https://ntfy.sh) 主題的工作群組面板：**顯示歷史訊息、即時推送新訊息**，
主題需要認證時可以輸入**使用者名稱/密碼或存取權杖**。

- 預設伺服器：`https://msn.feg.cn`（**介面上不顯示位址**，見「伺服器位址藏起來」）
- 側欄圖示：👥（面板名「團隊協同」，預設順序 60）
- 面板位置：`main` 面板，key = `ntfy-teams`
- 介面語言：**繁體中文**（與宿主介面一致）

---

## 一、怎麼用

1. 側欄點 👥 → 開啟「團隊協同」面板。第一次開啟時會自動訂閱預設群組
   `pub_dsh`（顯示名稱 **AIFE**）。
2. 點「**+ 訂閱主題**」，輸入主題名稱（例如 `pub_demo`），Enter。
   - 訂閱清單存在**外掛目錄旁的 `config.yml`**（宿主那一側），
     **外掛完全不使用 localStorage** —— 持久層只有這一份 YAML，換瀏覽器、換 profile、清快取都還在。
   - 最多 **8 個**主題。
3. 歷史訊息會自動載入，之後的新訊息由 SSE 即時推進串流。
4. 要傳訊息就在底部輸入框打字，**Enter 傳送、Shift+Enter 換行**。
   **要先填「顯示名稱」才能送**（訊息靠 `#名稱` 辨識是誰說的）。

### 訊息內容支援 Markdown

內文以 Markdown 呈現：標題（`#`/`##`/`###`）、**粗體**、*斜體*、~~刪除線~~、`行內程式碼`、**表格**、
圍欄程式碼區塊、有序/無序清單、引用（`>`）、分隔線、`[連結](https://…)`。

**表格**用 GFM 語法，支援對齊：

```
| 欄位  | 必填 |
| :---- | :--: |
| topic |  是  |
```

對齊標記 `:---`（左）、`:-:`（中）、`---:`（右）；最外側的 `|` 可以省略。
分隔列的格數**必須與表頭一致**，否則整段會當成普通段落（避免把普通文字誤判成表格）。
欄位多時表格自己橫向捲動，不會把版面撐破；格子裡的行內標記（粗體、程式碼、連結）照常解析。


> 內文**不會**被當成 HTML 解析 —— `<script>`、`<img onerror=…>` 只會以文字顯示。

### 發送者身分：`#username`

工作群組的約定：**訊息的 `title` 欄位就是發送者，格式為 `#username`。**

* 在共用設定的「**顯示名稱**」（例如 `shawoo`）填好，按「儲存」。
* 之後從面板送出的訊息，`title` 就是 `#shawoo`。
* **自己的訊息會靠右顯示**（頭像鏡射到內側、文字靠右），其他人維持在左邊 ——
  左右分邊是最快看出「誰說的」的方式。
* 收到的訊息若 `title` 是 `#xxx`，面板會顯示成該成員發的（頭像取名字首字、顏色由名字決定）。
* **只有 `#` 開頭的 `title` 才算發送者。** 沒有 `title`、或 `title` 是別的內容，都當成
  「沒有發送者」，名稱固定顯示成 **`--`** —— 版面格式與其他訊息**完全一樣**，
  只是名字是 `--`（不使用「未具名成員」這種說法）。那個 `title` 的內容不會被吃掉，
  會當成內文的標題顯示出來。

> **舊格式相容**：這個外掛早期用過 `@username`。解析現在仍然接受 `@`，
> 所以那個時期留下來的訊息不會突然變成「未具名成員」；但**顯示一律正規化成 `#xxx`**，
> 新送出的訊息也一律用 `#`。`senderTitle('@shawoo')` 會得到 `'#shawoo'`。
>
> 另外注意：`#` 只出現在**標題欄位**（`title`）。訊息內文的 Markdown `#` 標題不受影響。

### 主題別名（暱稱）

訂閱的主題可以另取一個顯示名稱，方便閱讀：

* **雙擊**任何一個主題 chip（或用鍵盤 `F2`），chip 會**就地變成輸入框**。
* 輸入新名稱後 **Enter** 或點到別處即生效；**Esc** 取消。
* **留空 = 用主題名** —— 清空輸入框就會把別名刪掉，顯示回原本的主題名。
* 有別名的 chip 會多一個小圓點 `•`，滑過去看 tooltip 可以同時看到「別名（原主題名）」。

**主題名本身不會被改**：別名只是顯示用的標籤，訂閱、收發、未讀計數都還是用原始主題名。
所以你可以把 `pub_demo_x7f2` 叫成「研發組」，而不影響任何通訊行為。

別名存在 `config.yml` 裡，重新整理後還在。

### 主題數量上限 8，預設主題受保護

**最多 8 個**主題（`core.MAX_TOPICS`）。到達上限時「+ 訂閱主題」仍可按，
但會擋下並說明：`最多只能訂閱 8 個主題（目前已有 8 個），請先取消一個再新增。`
——不把按鈕變灰（看起來像壞掉），而是告訴你該怎麼做。按鈕上也會顯示 `n／8`。

**`pub_dsh`（顯示名稱 AIFE）是固定錨點**：

* **永遠排在第一位** —— 不是靠「什麼時候被加進來」，載入既有設定後也會被糾正
  （`core.store.pinTopicFirst`）。
* **不可改名**（雙擊不開輸入框、`F2` 無效、`commitAlias` 也擋）。
* **不可取消訂閱** —— `×` 換成 🔒；`doRemove` 也再擋一次
  （刪除是破壞性動作，不能只靠「按鈕沒渲染」來保證）。
* 清單裡沒有它時會**自動補上**（無論其他主題有幾個），因為它既然不可刪，
  就不該有「不存在」的狀態。

### 取消訂閱要確認

按主題 chip 上的 `×` **不會直接刪掉** —— 會先出現確認條：

```
取消訂閱「研發組」？  (pub_demo_x7f2)              保留   取消訂閱
```

* **保留** 或 **Esc** → 什麼都不變，回到主題列。
* **取消訂閱** → 才真的移除，而且**立刻**寫回 YAML（不等 debounce，避免「刪完馬上重新整理」遺失）。

移除後**不會自己回來**：訂閱連線在收尾時可能還會收到伺服器送來的訊息或狀態，
這些資料一律被丟棄（`core` 只收「目前有訂閱」的主題的資料），
所以按了取消就是真的取消。

### 訊息列版面

每一列是「左邊一小塊（頭像 + 下方的時間）＋ 右邊內文」：

```
[頭像]   #alice    ← 名字
 10:24  訊息內容…

                #me  你  [頭像]      ← 自己的訊息整列靠右
              我的訊息…   10:24
```

* **時間放在頭像正下方**，並把這一小塊固定成 38px 寬 —— 這樣不管名字多長、
  內容幾行，左邊那幾列的頭像與內文起點都在同一條線上，整串讀起來是整齊的兩欄。
  時間寬度若會撐開這一塊，就會把內文推來推去（這正是做這個調整的原因）。
* 沒有時間的訊息**不畫時間元素**（而不是畫一個空的），否則那幾列會多出間隙、
  比別人高一點。
* 自己的訊息維持整列靠右（頭像在內側、時間在頭像下方）。
* 訊息區左右都留白，**右邊多一些**（左 26px、右 44px）：自己的訊息靠右，
  多留一點右邊白才不會整個貼著邊框。日期抬頭與空白狀態都用同一組留白。

### 訊息列隔行底色

相鄰的訊息列用**很淡**的底色交錯，方便橫向對齊閱讀，但不會濃到變成色塊：

* 只用一層 **3%** 的墨色混色（`color-mix(… var(--dsw-alias-label-primary) 3%, transparent)`）。
  刻意用「墨色」而不是 `bg-layer-1`：淺色主題下 `bg-layer-1` 與底色一樣是純白，
  白疊白等於完全看不出來（實測對比 1.000）。改混墨色後深淺主題都是約 1.06 的淡差異。
* 序號**跨「天」連續累計**，所以中間夾了日期抬頭也不會出現兩行同色相鄰。
* **自己的訊息維持原本較明顯的底色**（「自己說的」比隔行交錯更重要）。
  所以 `--self` 規則必須排在 `--alt` 之後，順序反了就會被隔行底色蓋掉。
* 滑過去的底色用同一種墨色混 7%，深淺主題都看得出來
  （淺色主題的 `bg-layer-1`／`bg-layer-2` 都是純白，拿它們當 hover 等於沒變化）。

### 右側面板（看板佔位）

訊息串右邊有一格**可以拖寬**的面板，目前是佔位（寫著「看板／即將推出」）：

* **最小 200px**；拖曳把手在面板左緣，平時是一條很淡的線，滑過或聚焦才亮起來。
* **寬度會記住**（存在設定 `dashboardWidth`），重新整理後還是你拉的那個寬度。
* 也可以用鍵盤調：把手聚焦後 `←`／`→` 每次 16px、`PageUp`／`PageDown` 每次 64px。
* 拖到極窄會被夾在 200px；拖太寬會被夾在上限，免得把訊息串擠到看不見。

未來看板要做成「未結待辦／今天的決定／成員活躍度」這幾張卡 —— 資料來源就是上面
那批 `Tags`，所以不必另建儲存。換內容時只要把佔位換掉，版面不用再動。

### 依日期折疊

訊息串會依「天」分組，每天的抬頭是一顆**可以按的按鈕**。
**預設只有「今天」展開，其他日子一律折起來** —— 打開一個群組不該先被幾百則舊訊息
淹沒，要回顧哪一天再自己點開：

* **未讀所在的那一天會強制展開**：折疊是為了少干擾，不是為了把新訊息藏起來。
  如果未讀線落在被折起來的日子裡，那一天會自動打開。
* 每一天的抬頭都標了則數，折起來也知道漏掉幾則。

```
⌄ 今天  2 則
```

* 按一下就把**那一天收起來**（抬頭變成 `› 今天  2 則`），再按一下展開。
* 抬頭右邊固定顯示那天的則數，收起來也知道漏掉多少。
* **折疊狀態一旦決定就只由使用者的點擊改變**：新訊息進來不會把你手動收起來的那天
  又打開（初始值用 lazy initializer 只算一次）。唯一的例外是下面那條「未讀所在的那天」。
* **初始值**：只有「今天」是展開的，其他日子全部折起來。
* 新訊息進來時，如果它剛好落在被收起來的那一天，**會自動展開** ——
  不會出現「有訊息但看不到」。其他被收起來的日子不受影響。
* 沒有 `time` 欄位的訊息歸到「沒有時間」一組，**那組保持展開**，一樣可以收。

#### 日期跳轉列（訊息串右側中央）

訊息串右緣固定著三顆按鈕，**垂直置中**，用掉原本空著的右側內距：

```
┌──────────────────────────┐    ┌───┐
│  ⌄ 昨天  18 則            │    │ ↑ │  ← 上一天的第一則
│    訊息…                  │    ├───┤
│  ⌄ 今天  18 則            │    │ ↓ │  ← 下一天的第一則
│    訊息…                  │    ├───┤
│                          │    │ ⤓ │  ← 最後一則（END）
└──────────────────────────┘    └───┘
```

* **↑ 上一天**：跳到前一天的第一則訊息。
* **↓ 下一天**：跳到後一天的第一則訊息。
* **⤓ 最後一則**：直接捲到底（最新的訊息）。
* 只有一天時，上／下一天會變淡且不可按（位置不跳動），「最後一則」仍可用。
* 完全沒有訊息時整列不出現。

捲動只動訊息串本身，不會連外層頁面一起跳。

#### 日復盤：把某一天的對話帶進新 session

每一天的抬頭右側有一顆 **`?`（提問）按鈕**。按下去會：

1. 用**那一天在該主題的訊息**組成一份種子內容；
2. 開一個**新的對話 session**（由宿主半邊的 `POST /ntfy-teams/session` 建立）；
3. 讓你直接就那天發生的事提問 —— 不必手動複製貼上。

種子 session 的契約（踩過坑，有回歸測試）：

* `seed` 事件的 `seq` **必須從 0 開始且連續**（`seq: 1` 開頭會被拒）。
* 有 `seed` 就必須帶 `inheritedEventCount: 0`。

### 焦點中的主題：什麼時候自動跟隨、什麼時候提示未讀

正在看某個主題時，新訊息進來會依「**是不是自己發的**」和「**有沒有貼在底部**」分三種處理：

| 情況 | 行為 |
|---|---|
| **自己發的** | 一定算已讀（那是你剛送出去的） |
| **別人發的，而且你貼在底部** | 算已讀 —— 你正看著它出現，不需要再提示 |
| **別人發的，而你往上翻了歷史** | **算未讀**，畫面底部浮出「**N 則新訊息**」提示條 |

提示條就在訊息串右下方（日期跳轉列旁邊），**點一下就跳到第一則未讀**，
並把這些訊息標成已讀、提示條消失。

反之，如果你往上翻歷史時**自己**發了一則，**不會**把你硬拉回底部 ——
你正在讀的東西不該被搶走；那一則的位置會由提示條告訴你。

> 這解決的是一個很煩的舊行為：以前只要面板開著就一律自動跟到底，
> 你在翻上週的對話時，別人一說話畫面就被拉走。

### 永遠滾到最新：不管誰發的訊息都自動捲到最底

輸入框上方**第二個** checkbox（綠色，同樣**預設關閉**、每個主題各自一份）：

```
☑ 永遠滾到最新：不管誰發的訊息都自動捲到最底
```

勾選後，這個主題**永遠**跟著最新訊息走 —— 別人發的也捲，不像預設行為只跟隨自己發的。
勾選的當下會**立刻**捲到底（不然會覺得「勾了沒反應」）。

**它跟「N 則新訊息」提示條的關係**：

| 開關 | 別人發訊息時 |
|---|---|
| 關（預設） | 不搶走畫面，浮出「N 則新訊息」提示條讓你自己決定 |
| 開 | 直接捲到最底（提示條也就不會出現，因為你已經看到最新了） |

**什麼時候該開**：你在盯一個正在熱烈討論的主題（或 CI 通知），希望畫面一直跟著跑。
**什麼時候該關**：你想好好讀一段歷史 —— 那時候被拉走很煩。

> 注意：這個模式跟「提示未讀」是**互斥的取捨**。開著就是放棄「晚點再看」的保護。

設定住在 `config.yml` 的 `stayAtBottom`（`{ 主題: { on } }`）。

### 自動回應：出現 `/approve session` 就回 `/approve`

輸入框上方有一個 checkbox（**預設關閉**，每個主題各自一個）：

```
☑ 自動批準 /approve
```

勾選之後，**這個主題**收到符合條件的訊息時，會自動以你的名義回一則 `/approve`。
勾選時整列會變成淡藍色，一眼看得出「現在是開的」。

**會延遲 10 秒，期間可以取消**：判定通過之後不會立刻送出，而是把那顆膠囊變成
琥珀色的倒數狀態 ——

```
☑ 自動批準 7s    [取消]
```

倒數跑完才真的送出；按「取消」就不送（**開關本身不會被關掉**）。
切換主題也會取消待送出的。

> 這個延遲是**安全機制**，不是為了好看：ntfy 沒有「撤回」，送出去就收不回來，
> 而自動批準是「代替你發言」。這 10 秒讓你在看到內容不對時來得及喊停
> （例如那句話其實是在討論、不是在請求核准）。

**觸發條件（三個都要成立）**：

| 條件 | 說明 |
|---|---|
| 內文含 `/approve session` | 完整片語；只寫 `/approve` 不會觸發 |
| **訊息帶 `hermes-agent` 標籤** | `/approve session` 是任何人都能打出來的普通字串 —— 加上標籤才把觸發面縮到 Hermes agent 產生的請求 |
| 是**即時推送**（不是歷史） | 面板一打開載入的舊訊息不會被回一遍 |

標籤比對**不分大小寫**、忽略前後空白，而且只要 tag 清單裡**含有**它就成立
（同一則訊息可以同時帶別的標籤）。

**這是會代替你發言的功能**，所以另外還有三道防線：

| 防線 | 為什麼 |
|---|---|
| **不回應自己發的** | 否則你回的 `/approve` 又被判定成觸發 → 無限循環 |
| **同一則只回一次** | 已回過的訊息 id 記在 `config.yml`，重新整理也不會重複回 |
| 沒設定顯示名稱時不回 | 送出的訊息會是無名訊息，對群組沒有意義 |

設定住在 `config.yml` 的 `autoApprove`（`{ 主題: { on, ids } }`）；`ids` 只留最近
50 筆，目的是「不要對同一則回兩次」，不是完整歷史。

### 沒有打開面板也會收到（角標才會動）
即時連線（SSE）掛在**外掛層**，不是掛在面板上：

* 面板是由宿主提供的頁面，**切到別的頁面時宿主會把整個面板從 DOM 移除**。
  如果連線跟著面板走，那「沒打開就完全收不到訊息、角標永遠不動」——
  而角標存在的意義正是「沒打開也知道有沒有人找你」。
* 所以連線在 host 這一層建立，主題清單或伺服器一改就自動重連；面板只負責顯示。
* 未讀**不落盤**（不使用 localStorage）：角標是「這次開啟期間」的狀態，重新整理後歸零。

**「正在看」的判定**：必須「該主題是目前主題」**而且**「面板真的顯示著」。
只看前者會把「面板關掉之後來的訊息」全當成已讀 —— 這是最容易搞錯的地方。

### 未讀提示與「上次讀到哪」

未讀不為 0 時有**兩層**提示，而且切換主題會自動捲到上次讀到的地方：

* **主題 chip**：未讀時把邊框點亮、顯示數字角標，tooltip 也會寫「未讀 N 則」。
* **訊息串裡一條未讀線**：切到該主題後，會在**上次讀到的那一則之後**畫一條
  「N 則新訊息」的分隔線，並自動捲到它，讓你從斷掉的地方接著讀。
  那條線會**留著**（不會一出現就被清掉），作為「我上次讀到這裡」的參考點。
* 會記住每個主題「**上次讀到哪一則**」（`lastReadIdByTopic`，有持久化），
  所以下次打開才畫得出這條線。
* **只在真的看得到時才算已讀**：未讀線捲進視野之後才把「讀到哪」推進到最新，
  不會東西還沒看到就被標成已讀。

> **找不到上次讀到哪就不畫線**：例如歷史已被上限裁掉、或第一次打開這個主題。
> 寧可不畫，也不要整串被誤標成「新訊息」。

### 已讀 / 未讀與側欄數量角標

側欄「團隊協同」那一列的圖示右上角會顯示一個紅色角標，內容是**所有主題的未讀總數**
（超過 99 顯示 `99+`）；沒有未讀時角標不出現。

計數規則（與一般群組軟體一致）：

| 情況 | 是否計入未讀 |
|---|---|
| 即時（SSE）收到、且該主題**不是**目前主題 | ✅ 計入 |
| 即時收到、但就是目前主題 | ❌ 不計 |
| 歷史訊息載入 | ❌ 不計 |
| 自己送出的訊息 | ❌ 不計 |

**看過就清零**：切換到該主題（點面板裡的 topic chip）會把它的未讀歸零，角標隨之消失。
未讀數量只活在記憶體 —— 這個外掛不使用 localStorage，所以**重新整理後角標歸零**。

> **角標位置**：在**標題文字的右邊**，不是疊在圖示上（早期版本會蓋住圖示，
> 已修正）。因為宿主那一列只提供「圖示」這個座位（`sidebar.panellist`，props 只有
> `size` / `active`），標題是**宿主自己的元素**、DOM 順序上在插槽之後，所以純 CSS
> 排不過去 —— 只能絕對定位，而且位移必須**量出來**
> （`positionUnreadAfterTitle()` + `ResizeObserver`），因為它隨標題長度改變：
> 實測標題 56px 時位移 86px、標題 196px 時位移 226px。
>
> **連線狀態燈（LED）**貼在圖示的右下角（9px，只壓到 16px 圖示約 1/4），
> 顏色區分狀態、形狀也區分（✓ / ✕ / ! / … / • / 轉動的圓弧），
> 所以色盲也能分辨。狀態優先序：`retrying > error > offline > connecting > unread > idle`。

### 認證

`ntfy` 的規則是：**`pub_` 開頭的主題不需要認證；其他主題讀取時一定需要認證。**

### 失敗會自己重試：1s → 2s → 4s → 8s → 16s → 30s

連線或歷史請求失敗時**不會就此放棄** —— 會依固定節奏重試，到 30 秒後固定每 30 秒再試
（`backoffFor`）。**永不停止**：429 是暫時的，放棄等於「這個主題從此不再更新，
直到使用者手動重新整理」，那比慢一點連上糟得多。

為什麼是查表而不是現算 `2^n`：需求指定的那串數字裡 **16→30 不是 2 的次數**
（32 被截成 30）。查表讓實作與規格一字不差。

多個主題同時失敗時會**加一點隨機抖動**（0–400ms），避免全部在同一毫秒醒來再打一次。

| 情況 | 重試？ | 為什麼 |
|---|---|---|
| `429`（限流） | ✅ 1s→…→30s，永不放棄 | 短窗口、小額度，等一下就恢復 |
| 連不上（status 0） | ✅ 同上 | 網路暫時問題 |
| `5xx` | ✅ 同上 | 伺服器暫時問題 |
| `401` / `403` | ❌ | 重試沒有意義，要使用者先去改設定 |
| 其他 `4xx`（404…） | ❌ | 重試不會變好 |

**側欄圖示會顯示「等待重試」**，而不是看起來像壞掉：

| | 一般錯誤 | 等待重試 |
|---|---|---|
| 形狀 | 三角形＋驚嘆號 | **轉動的圓弧＋箭頭**（有動畫） |
| 顏色 | 錯誤色 | 警告色（它會自己好） |
| tooltip | 「全部主題連線失敗」 | **「等待重試（8 秒後重試）」——倒數會動** |

倒數不是寫死的字串：側欄在重試期間每 500ms 重繪一次，秒數由 `status.retryAt` 現算。
尊重 `prefers-reduced-motion`（不轉動，但仍用形狀區分）。

> **怎麼分辨「重試中」與「真的壞了」**：`status.retryAt > 0` 就是重試中。
> 沒有這個欄位（例如 401）就當一般錯誤 —— 前者會自己好，後者要使用者動手。

### 伺服器、帳號、顯示名稱：**全域只有一份**

這三樣**只有一份**，跟訂閱幾個主題無關。但**伺服器不可由使用者修改、介面上也沒有那個欄位**
（見下方「伺服器位址藏起來」），所以共用設定只收兩項，預設只顯示一行摘要：

```
無認證 · 以 #shawoo 傳送                              全部主題共用   [編輯]
```

按「編輯」（或右上角 ⚙）才展開：

| 項目 | 說明 |
|---|---|
| 顯示名稱 | 送出訊息時的 `#username`（全域一份）。**沒填就不能送訊息** |
| 認證 | `無認證` / `帳號密碼` / `存取權杖` |
| 帳號密碼 | 走 HTTP Basic（`Authorization: Basic …`） |
| 存取權杖 | 走 Bearer（`Authorization: Bearer tk_…`） |
| 測試連線 | 打一次 `/v1/health` 確認連線 |
| 儲存 / 清除憑證 | 寫入或清除外掛目錄旁的 `secrets.yml` |

某個主題回報需要認證時，這個區塊會**自動展開**並提示。

面板是工作群組版面：頂部有群組抬頭（群組名 + 主題數）與連線狀態徽章，
中間是帶頭像與發送者的訊息串（依日期分段），底部是撰寫區。

> **憑證存在外掛目錄旁的 `secrets.yml`（權限 `0600`），由宿主半邊讀寫。**
> `core` 裡**以伺服器位址分桶** —— 不是分主題：同一個伺服器上不管訂閱幾個主題，
> 都只有一份帳號。它不會寫進外掛原始碼、不會被 log 出來、也不會送到除了該 ntfy
> 伺服器以外的任何地方。
>
> **已知界線（不迴避）**：宿主有一條 `GET /ntfy-teams/settings` 會**把憑證明文回給
> 客戶端** —— 訂閱私有主題就需要它。那條路徑只綁 `127.0.0.1`，所以能打到它的對象
> 與能直接讀 `secrets.yml` 的對象是同一批，不擴大實質暴露面。但**若哪天這個 Web
> 入口被開到外網，這裡就會變成把密碼送出去的地方** —— 那時必須改成不回傳憑證。
>
> **伺服器位址藏起來（刻意的產品決定）**：預設伺服器 `https://msn.feg.cn` 是管理者
> 提供的後端，一般使用者**不能改、也不需要知道**。所以：
> * 共用設定裡**完全沒有伺服器欄位**（連輸入框都沒有）；
> * 面板抬頭也不顯示主機名；
> * tooltip／`title`／輸入框的 `value`／`placeholder` 都不放位址
>   （`core.redactDefaultServer()` 負責清洗任何要顯示的字串）。
>
> 伺服器位址仍然存在 `config.yml` 裡（由外掛設定決定），憑證也照那個位址分桶 ——
> **只是沒有 UI 可以改它**。
>
> ⚠️ **這擋不住 DevTools**：外掛是瀏覽器**直接**連 ntfy，所以 Network 面板與 console
> 錯誤裡仍然看得到 `https://msn.feg.cn/...`。要真正在瀏覽器端隱身，得加一層宿主代理
> （瀏覽器只跟 `127.0.0.1:3080` 說話）—— 那是架構改動，**已明確決定不做**
> （見「為什麼宿主半邊不做 ntfy 代理」）。

### ★ 為什麼 `lib/client.js` 是建置產物

`dsh-client-modules` 只把**一個** client 檔案送上瀏覽器 —— 它解析 `package.json` 的
`exports["./client"]`，就只有這一個路徑，沒有「額外檔案」欄位，第三方檔案也不會被
組合進 combo script。所以隔壁的 `lib/core.js` 永遠不會被執行：實務上
`GET /plugins/ntfy-teams/core.js` 是 404，送出的 bundle 裡也找不到 core 的程式碼。

而**檔案順序也不能依賴**：combo script 會把每個外掛檔案包成 lazy body，檔案在
「註冊階段」並不會執行。只有「同一個檔案」才能保證先註冊、後 materialize。

因此 `build.js` 把 `lib/core.js` 的全部內容內嵌進 `lib/client.js` 的
`@@CORE_BEGIN@@ … @@CORE_END@@` 區塊，`lib/client.js` 因此是**自足**的。

```powershell
node build.js      # 改完 lib/core.js 之後一定要跑
```

`build.js` 會在寫出前用 `vm.Script` 驗證產物語法，並檢查內嵌區塊沒有殘留
`module.exports`（factory 自己有 local `module`，殘留的 Node 出口會讓整個 factory
拋錯）。**不要手改 `@@CORE_BEGIN@@` / `@@CORE_END@@` 區塊內的內容** —— 下次建置會覆蓋。

> 這一段是踩過坑寫的：先後試過「靠檔案順序」與「隔壁檔案 + `require`」，
> 結果都是面板顯示「核心模組未載入」；是瀏覽器端到端驗證才抓到的。

### 為什麼宿主半邊不做 ntfy 代理

`msn.feg.cn` 對所有路徑都回 `Access-Control-Allow-Origin: *`，而且預檢允許
`Authorization` 標頭，所以瀏覽器可以**直接** fetch JSON、直接讀 SSE ——
不需要像 `today-material-panel` 那樣為了繞開 CORS 在宿主側開代理路由。
少一跳代理就少一份狀態、少一處可以失敗的地方。

> **代價（刻意的取捨）**：因為是瀏覽器直連，**伺服器位址在 DevTools 裡看得到**
> （Network 面板、console 錯誤）。介面上藏得住，工具裡藏不住。
> 加這層代理是唯一能真正隱身的方法，但**已經決定不做** ——
> 需求是「伺服器功能不改」，而且少一跳就少一份狀態、少一處可以失敗的地方。
>
> 宿主半邊仍然存在，但只做兩件事：**建立種子 session**（把一天的訊息帶進新對話，
> 給「日復盤」用）與**讀寫 YAML 設定**。這兩件事都不碰 ntfy 流量。

### 為什麼 SSE 不用 `EventSource`

`EventSource` 不能帶自訂請求標頭，所以帶認證的主題會拿不到串流。
`core.subscribeTopic()` 改用 `fetch()` + `response.body.getReader()` 自己切
SSE 框架，這樣 `Authorization` 才送得出去。

### 即時推送不是輪詢 —— 沒有定時打 API

外掛**完全沒有**定時輪詢。唯一的週期性計時器是側欄重試倒數的 500ms 重繪
（`setInterval`，只在「等待重試」時開），它不發任何網路請求。

| 請求 | 什麼時候發 | 幾次 |
|---|---|---|
| `GET /<a,b,c>/sse` | 開機建立，之後**一直掛著** | 1 條長連線 |
| `GET /<a,b,c>/json?poll=1&since=all` | 開機載入歷史（循序、間隔 400ms） | **一次性** |
| `GET /v1/health` | 只有按「測試連線」時 | 手動 |

> **`poll=1` 不是「輪詢」**：那是 ntfy 的參數名，意思是「把快取訊息回完就關閉連線」，
> 相對於 SSE 的「開著不回」。外掛只在開機時用它抓一次歷史，**不會重複呼叫**。
>
> 實測（瀏覽器攔截 `fetch`，乾淨頁面開著觀察 30 秒）：**總共 0 個新請求**。
> 連線靠 SSE 長連線推播，伺服器以 keepalive 事件維持它。

### 側欄狀態：`live` 與 `idle` 是兩件事

* **`live`（已連線）**：SSE 正常掛著、沒有未讀 —— 這是**健康**狀態。
* **`idle`（尚未訂閱主題）**：一個主題都沒有。

這兩者原本共用 `idle`，於是「SSE 正常運作」跟「什麼都沒有」在畫面上長得一模一樣 ——
使用者因此合理懷疑「是不是沒在用 SSE／是不是在輪詢」。現在分開了，
`live` 的說明文字也直接寫出「SSE 已連線」。

完整優先序：`retrying > error > offline > connecting > unread > live > idle`。

### 串流結束會重連（不只是「錯誤」才重連）

連線層有兩條路徑**不會**走 `onError`：

* 串流**自然結束**（伺服器收尾、被中間設備切斷）；
* `AbortError`（網路中斷）。

只從 `onError` 重試的話，這兩種情況會停在 `offline` —— **沒有重試、永遠「未連線」**。
所以 `subscribeTopics` 多了 `onClosed` 回呼：只要是**非主動**的結束就通知訂閱方，
由它依同一套退避節奏重連。

主動 `close()`（切換主題、關閉面板、外部 signal 取消）**不會**觸發 `onClosed`，
否則會變成「自己關 → 自己重連」的迴圈；已經報過 `onError` 的失敗也不會再補一次
`onClosed`，避免重試兩次。

### 一條 SSE 連線訂閱所有主題（不是每個主題一條）

ntfy 支援在路徑放**逗號分隔的主題清單**：`/pub_a,pub_b/sse`（實測本伺服器可用）。
所以 `core.subscribeTopics(server, ['pub_a','pub_b'], …)` 只開**一條**連線，
再按每則訊息自己的 `topic` 欄位分發。

| | 之前 | 現在 |
|---|---|---|
| 5 個主題 | **5 條**常駐連線 | **1 條** |
| 限流消耗 | 5 次 | 1 次 |
| 重試狀態 | 每個主題各一份 | 整條連線一份 |
| 訊息順序 | 各連線獨立，可能交錯 | 共用一個到達順序 |

實測（瀏覽器攔截 `fetch`）：訂閱清單一變只發 **1 個** `/sse` 請求，
URL 是字面的 `pub_dsh,pub_probe/sse`。

**三個實作要點（都是踩過的）**：

1. **逗號不能被編碼**。`encodeURIComponent('a,b')` 會變成 `a%2Cb`，ntfy 就讀不到
   「多個主題」的意思 —— 必須**逐段編碼再接起來**。
2. **`open` 事件的 `topic` 是整串清單**（例如 `"pub_a,pub_b"`），但**每則訊息的
   `topic` 只有一個**。所以分發只看訊息，不看 open。
3. **認證是整條連線的事**：ntfy 只要有一個主題沒權限就整個請求回 `403`，
   不會只擋那一個 —— 所以錯誤與 `authRequired` 要記在**所有**訂閱中的主題上。

`subscribeTopic(server, topic, opts)` 保留為單主題的薄包裝（簽名不變），
內部就是 `subscribeTopics(server, [topic], opts)`。

> 分發時主題名稱**不做 `normalizeTopic`**：主題名可能含大寫，而訂閱時送出的
> 就是原始名稱，硬正規化會對不上。用 trim 後的原字串直接比對。

### 載入順序（重要）

* `lib/client.js` 是**唯一**註冊 `__ModuleLoader__.load({ id: 'ntfy-teams', … })`
  的檔案 —— 一個檔案只能註冊一個 factory，id 必須等於套件名，而且它必須**自足**。
* `lib/core.js` 的程式碼由 `build.js` 內嵌進 `lib/client.js`；它本身留在磁碟上
  是為了 `node test/core-*` 與維護方便，**不會**被送到瀏覽器。
* 兩個檔案都必須在 `package.json` 的 `files` 裡，否則不會被安裝進去。

### 訂閱清單的儲存：**唯一真相是 `config.yml`**

`core.store` 是**純狀態**，刻意不做任何儲存 I/O（「無副作用」原則）。
主題清單的持久層是**宿主那一側的 `config.yml`**，不是瀏覽器：

```
PUT /ntfy-teams/settings  →  lib/config-store.js  →  config.yml（原子寫入）
GET /ntfy-teams/settings  ←  啟動時同步回來
```

**這個外掛完全不使用 localStorage。** 持久層只有一個 ——
宿主那一側的 `config.yml`（設定）與 `secrets.yml`（憑證）：

```
PUT/POST /ntfy-teams/settings  →  lib/config-store.js  →  config.yml
GET      /ntfy-teams/settings  ←  啟動時同步回來
```

瀏覽器這一側只需要記住「這次開啟期間」的值（core 用一個記憶體物件當儲存）：
開機時從 YAML 讀進來、使用者的變更寫回 YAML，重新整理就重建。

> **訊息不落盤**：歷史改成**開啟時重抓**，而且**只抓當前主題**（切過去才抓下一個），
> 因為 ntfy 的額度實測只有約 6 次／短窗口 —— 開機就對每個主題各抓一次會把額度吃光。
> 代價是重新整理後未讀角標歸零。

**為什麼要拿掉 localStorage**（這是花了好幾輪才收斂的結論）：它與 YAML 是**兩個真相**，
而 store 又會從快取把資料撈回來，於是出現一整類 bug：

1. 「取消訂閱 → 重新整理又出現」：宿主已經刪了，store 卻從快取撈回舊主題
   （同步那段只 `ensureTopic`「只加不減」）。現在同步 = 讓 store **等於**宿主的清單。
2. 「刪完馬上重新整理就遺失」：寫回宿主是 400ms debounce，排程被卸載吃掉。
   現在破壞性動作走 `writeSettingsNow()`（立刻寫），並在卸載時用 `sendBeacon` 補送。
3. 「換瀏覽器就把主題清單蓋掉」：開機時 store 還是空的，一個提早的寫入就把宿主的
   完整清單覆蓋成當下那一兩個。現在首次同步完成前**不準寫**（只排隊，之後補送）。

### 主題排序與預設主題

* `core.store.pinTopicFirst(topic)` 把某個主題移到最前面，其餘保持相對順序；冪等。
* `ensureDefaultTopic()` 的語意是「**確保存在**」，不是「只在全新安裝播種一次」。
  曾經寫成後者，結果已經有主題的使用者**永遠**看不到預設主題 ——
  「預設」於是只對第一天的使用者成立。
* 它同時受 `protectedTopic()` 保護（不可改名／不可刪除），所以補回來不會違反使用者意圖。

### Markdown 與身分

* 解析在 `core.parseMarkdown()`（純函式、可單測），UI 只把 AST 變成 React 節點。
* UI **不使用 `dangerouslySetInnerHTML`**：所有文字都走 React 的文字節點，所以
  `<script>`、`<img onerror=…>` 只會以文字顯示。
* 連結只有 `http`/`https` 會變成 `<a>`。危險連結（`javascript:` 等）由
  `core.parseMarkdown()` 在**產生節點之前**就退化成純文字 —— 瀏覽器實測
  `[click me](javascript:alert(1))` 會逐字顯示，DOM 裡沒有任何 `<a>`。
  `client.js` 另有一道 `.ntfy-teams-md-rawlink` 的縱深防禦，但正常情況下不會被觸發
  （實測出現 0 次）。
* 身分：`title` 欄位放 `#username`。`core.parseIdentity()` 解析、`core.senderTitle()`
  組裝（冪等，不會產生 `@@x`）、`core.setIdentity()/getIdentity()` 存取設定。

### 優先級：就是送出鈕本身的顏色

優先級跟「傳送」按鈕**合為一顆** —— 按鈕的顏色＝目前的優先級，所以按下去之前
就知道這則訊息多大聲：

```
┌───────────────────────┬──────────────┐
│  ‹   ▂▄▆   ›          │  ➤  傳送      │
└───────────────────────┴──────────────┘
   前後箭頭調整級別          送出
```

| 級別 | 顏色 | 強度格 | 意義 |
|---|---|---|---|
| 最低 | 淡灰 | ▂ | 純記錄，不通知 |
| 低 | 藍 | ▂▄ | |
| 預設 | **黑／白（跟隨主題）** | ▂▄▆ | ntfy 的 `normal`，**會觸發手機推播** |
| 高 | 紅 | ▂▄▆█ | 打穿勿擾 |

* **‹ ›（前後箭頭）調整**：一次一級，**到頂／到底會停用**（不循環），
  所以「已經到底了」看得出來。兩個按鈕之間**留 7px 空隙**，避免想按送出卻按到箭頭。
* **上面那顆跟傳送不是同一顆**：調級別一塊、送出另一塊，中間留白隔開。
* **切換主題就回到預設**，而且**刻意不保存**（不進 `config.yml`、
  不進 localStorage，重新整理也是預設）。

**為什麼不做成「換級別時就送出」**：送出是**無法撤銷**的動作。把「打字打到一半
誤觸」變成「送出一則錯誤訊息」，代價太高 —— 顏色已經讓兩件事看起來是一體，
不需要連動作也合併。

**為什麼「預設」的顏色會跟著明暗反轉**：它是打開面板時的預設值，要的是
「一個**高對比的中性色**」—— 淺色主題下是黑、深色主題下就該是白。
所以用會反色的 `--dsw-alias-label-primary`，**不是**固定色票
`--dsw-static-neutral-900`（那個在深色下仍是 `#0f0f0f`：
深色底配深色字，整顆看不見）。

**走過的路**（每一代都保留在 HANDOFF 裡）：
`<select>` 下拉框 → 四段帶文字的分段控制 → 四格階梯（**每格只有 7×16px，
幾乎按不到**）→ 併進送出鈕 → 前後箭頭、去掉文字、尺寸 90%、深淺色都能讀。

### 訊息時間

本伺服器發出的 `id` 是**隨機字串**，不是時間編碼（實測 8 組樣本，任何位元組解讀、
任何端序、任何 ms/ns 縮放都對不上 `time` 欄位）。因此 UI **一律採用伺服器給的
`time` 欄位**；`core.decodeId()` 只是有界兜底，對本伺服器會安全地回 `null`，
寧可顯示空白也不編出一個荒謬的年份。

### 認證的錯誤碼

實測：**沒帶憑證 → `403`**（反向代理直接擋掉）；**帶了但憑證錯誤 → `401`**。
`core` 把兩者都歸為 `authRequired: true`，UI 據此自動展開連線設定列。

## 三、測試

```powershell
node test/core-node.js         # 142 項，離線（含 Markdown 表格/fuzz、100 KB 效能、主題別名、未讀邊界、主題上限、預設主題）
node test/config-store-node.js # 19 項，YAML 產生／解析（含空容器、特殊字元、原子寫入）
node test/host-node.js         # 27 項，宿主半邊（種子 session 的 seq 契約、路由）
node test/core-live.js         # 7 項，打真實 msn.feg.cn（⚠️ 打太頻繁會 429，見下）
node test/client-offline.js    # 42 項，離線
node test/zh-tw-check.js       # 介面文案必須是繁體（掃出簡體字）
```

> **`core-live` 會撞到限流**：ntfy 的額度實測是**約 6 次請求／短窗口**，
> 第 7 次開始 429，而且回應**不帶 `Retry-After`**。輕度超額約 5 秒恢復，
> 但被連續打滿要**安靜約 2 分鐘**才回來。所以這個測試失敗時先看是不是 429 ——
> 若是，等 1–2 分鐘再跑，不要當成程式壞了。

瀏覽器端到端（需要 GUI 跑在 `http://127.0.0.1:3080`）：

```powershell
node test/browser-verify.js probe     # 只驗證 CDP 管線
node test/browser-verify.js full2     # 選面板 → 訂閱 → 標記即時出現 → 身分/Markdown/安全
node test/browser-verify.js eval --expr "<運算式>"   # 自訂探測（見 test/_verify-*.png）
```

`browser-verify.js` 需要 Chrome（`C:\Program Files (x86)\Google\Chrome\Application\chrome.exe`），
用 `--remote-debugging-port` + Node 內建 `WebSocket` 講 CDP，**不需要 npm 安裝任何東西**。
它跑完會把主題（淺色/深色）還原成「跟隨系統」。

> ⚠️ **寫驗證探針前必讀**：`eval` 用的是**你的真實設定檔與真實伺服器配額**。
> 曾經多次因此把測試主題寫進使用者的 `config.yml`、或把 ntfy 額度打滿。
> 原則：**用拋棄式主題名、測完就還原；不要「先備份再還原」**——
> 如果污染源是記憶體裡的狀態，還原等於把污染寫回去（實測踩過）。

## 五、已知限制

* 面板裡的「重新載入」會重新拉一次完整歷史（`since=all`）。ntfy 的歷史介面沒有
  分頁游標，所以**沒有**「載入更多歷史」按鈕 —— 與其放一個按下去沒反應的鈕，
  不如不放。
* 面板的未讀計數依賴 `store` 的判定：只有在「即時（SSE）到達」且**「沒看到最新」**
  時才累加。「沒看到最新」＝ 面板沒開、或正在看別的主題、**或正在看這個主題但往上
  翻了歷史**（見上面「焦點中的主題」）。歷史載入不會製造未讀。
* 憑證存在外掛目錄旁的 `secrets.yml`（權限 `0600`），**不經過瀏覽器儲存**。
  但宿主有一條 `GET /ntfy-teams/settings` 會**把憑證明文回給客戶端**（訂閱私有主題
  需要它），那條路徑只綁 `127.0.0.1`。**同機的其他使用者**若能讀該檔案或打那條路由，
  就能拿到憑證 —— 共用機器的場合請改用存取權杖，並只給該 token 必要的最小權限。
* **伺服器位址只在介面上藏起來**：DevTools 的 Network／console 仍看得到
  `https://msn.feg.cn/...`，因為外掛是瀏覽器直連 ntfy（見「為什麼宿主半邊不做代理」）。
  真正隱身需要一層宿主代理，而**那個決定是不做**。
* ntfy 的限流是**真實且很小的**（實測約 6 次／短窗口）。外掛已用「一條 SSE 訂閱所有
  主題、循序拉歷史、429 退避重試」把尖峰壓下來，但**多開幾個分頁／多台裝置同時用**
  仍然可能撞到 429 —— 這時側欄會顯示「等待重試」並自己接回來，不會永久失敗。
* 「顯示名稱」是自由輸入的字串，沒有跟任何伺服器帳號綁定 —— 它只是訊息上的標示。
  也就是說**任何人都可以自稱任何名字**；ntfy 的 `title` 不是可驗證的身分。要真的
  辨識身分，請靠私有主題的認證，而不是靠這個欄位。
