DSH Web GUI 布局图谱 —— 座位（Slot）与视觉边界

每个方块 = 一个可见区域。「虚线」= 平台预留的空座位，你可以注册；「实线灰」= shipped 已占用； 「点线紫」= 由别的包声明、你通常不动。悬停任意方块看它的契约（key / kind / scope / ownerProps / 真实范例）。

空座位 · 可注册 shipped 已占用 别包声明 · 通常不动 scope: root scope: session scope: session-maybe ■ single ☰ list ⌗ keyed ⇉ chain

1 · 整页框架：三列 + 帧级浮层

root（single, root）是全站唯一被 shell 渲染的座位，由 ui-layout 的 AppFrame 占据。 AppFrame 是一个 CSS grid：grid-template-columns: 侧栏px | minmax(0,1fr) | 右栏px， 并在同一份 JSX 里 声明了 sidebar / main / rightbar / shell.overlay 四个子座位。
不要注册 root 或 sidebar —— 它们是 single，你会把整个框架顶掉。

2 · 左栏 sidebar —— 六个子座位

侧栏是纯组合：SidebarRootComponentProps = PropsRuntime<'sidebar'> & PropsRenderSlots<六个子座位> & InjectFace<SidebarRootInjected> & PropsLocale<'sidebar'>。 面板元数据是座位注册表 + locale 的只读投影，没有独立的写 API。

3 · 会话区：头部 → tabs → 会话体

用户说的「会话建立后的 tabs（会话、追踪）」精确对应 conversation.view（list / session）。 tab 由注册项投影成 ViewTab { id, label }，label 缺省回落成 id。

4 · 输入区：composerStack 的盒子层级（hero vs composer）

这一页是整个图谱最值得反复看的一张。左侧是 composer（有内容的会话）， 右侧是 hero（新建空会话）。差别只有一处，但它会造成"我的东西在新会话里不见了"。

5 · 设定弹窗：一个域，不是一个组件

要点：底座不渲染任何界面。渲染 shell 的是 ui-settings-general（它占 sidebar.settings）， 它自身零文案 —— 触发文案、面板标题、关闭的无障碍名、每个 section 的内容，全部来自注册者。 弹窗是模态：它不画在侧栏列里，而是盖在整个应用之上。

6 · 叠放层级（从下到上）

这张图回答"我的东西为什么被盖住了 / 为什么点不到"。层的顺序由架构决定，你只能选择坐进哪一层。

7 · 主题令牌地图

左边是"哪个区域归哪类令牌"的语义示意（不是逐元素的权威映射）；右边是三层令牌的分工与命名规则。 切换页头的「暗色主题」可以看到：这张图本身没有改任何组件规则，只换了令牌值 —— 这正是 presenter 的工作方式。
